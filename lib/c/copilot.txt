# Bibliotecas estandar de Rivo con nombres de Python

## Objetivo

Desarrollar una biblioteca estandar amplia, practica y facil de aprender para
Rivo, con nombres de modulos iguales a los de la biblioteca estandar de Python
cuando exista un equivalente. Por ejemplo: `json`, `math`, `csv` y `random`.
Las APIs y la mayor parte de cada biblioteca deben estar escritas en Rivo
(`.ro`), no en C ni en C++. Los programas deben poder resolver tareas comunes
importando bibliotecas de Rivo, sin tener que escribir ni enlazar C o C++.

El C que ya forma parte del compilador o del runtime puede proporcionar soporte
interno minimo cuando haga falta interactuar con el sistema operativo o con una
capacidad nativa. No debe convertirse en la implementacion publica de las
bibliotecas. Mantener esa frontera pequena, documentada y reemplazable.

Los nombres de este catalogo son nombres de modulos, no una promesa de que Rivo
copie toda la API o el comportamiento de Python. Cada modulo debe tener una API
idiomatica, documentada y probada en Rivo. Si una funcionalidad no tiene un
equivalente razonable en la biblioteca estandar de Python, no inventar un nombre
de Python: proponerla por separado como extension propia de Rivo.

## Como construirlas

- Tratar el catalogo de abajo como 100 modulos objetivo, no como 100 modulos ya
  implementados. Marcar una biblioteca como disponible solo cuando su codigo,
  pruebas y documentacion existan.
- Usar los nombres publicos de los modulos de Python tal como aparecen en este
  catalogo; no reemplazarlos por traducciones ni por nombres propios de Rivo.
- Crear APIs pequenas, coherentes y especificas de Rivo. Empezar por las
  operaciones esenciales y ampliar segun necesidades reales.
- Reutilizar e importar bibliotecas de Rivo existentes en lugar de duplicar su
  funcionalidad. Mantener cada modulo enfocado y con responsabilidades claras.
- Preferir implementaciones portables en Rivo. Si una operacion requiere soporte
  nativo, limitarlo al compilador/runtime y ofrecer errores claros cuando no se
  admita en una plataforma.
- Acompanar cada modulo implementado con pruebas, ejemplos y documentacion de
  sus funciones, tipos, errores y limitaciones.
- Migrar o retirar una implementacion C solo despues de que exista un reemplazo
  equivalente en Rivo y sus pruebas pasen. No borrar soporte del compilador o
  runtime sin comprobar antes sus usos.
- Priorizar primero las bibliotecas comunes y pequenas; abordar formatos,
  sistema y redes despues; dejar las capacidades complejas para fases
  posteriores.
